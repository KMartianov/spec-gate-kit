## 0. Что уже правильно (не ломать)

- **flip-before-hash**: сначала флип `` `draft` ``→`` `approved` `` + строка `Утверждено`, затем sha256 получившегося
  содержимого. Хеширование до флипа сделало бы запись вечно невалидной.
- **Человеко-инициируемость**: CLI не вызывает агент; запись пишется только явным запуском человека.
- **Запрет «не-спеки»**: файл без строки `**Статус спецификации:**` отвергается.
- **Формат записи** `{root, spec, spec_sha256, task, approved_by, approved_at}` и каталог
  `$HOME/.local/share/opencode/approvals/<sha256(root)[:16]>/` — совместим со всеми читателями.
- **Обход корня** с ограничителями `.git` / `$HOME` / `/`.

## 1. P0 — корректность и доверие

### P0-1. Повторное одобрение молча инвалидирует доказательства (evidence v2)
`mark_approved` **всегда** переписывает строку `Утверждено` новым ISO-таймстампом → байты спеки меняются → меняется
`spec_sha256` → все существующие `verify/<id>.json` этой спеки хранят **старый** хеш → `spec-status` видит рассинхрон →
состояние падает `DONE → VERIFY`. Докстринг называет это «idempotent».
**Риск:** человек повторяет `spec-approve` «на всякий случай» и молча теряет весь прогресс DoD по спеке.
**Правка:** если спека уже `approved` — **не переписывать файл** (stamp не трогать); печатать
`already approved, unchanged (sha256 <short>)`. Обновление stamp — только явным `--restamp`, с предупреждением
«evidence для этой спеки станет stale».
**DoD:** два запуска подряд → sha256 файла во втором запуске не изменился, exit 0.

### P0-2. Нет резолва slug → `cwd/.slim/spec/<arg>`
`resolve_spec` делает только `Path.cwd()/arg` → при bare-slug файл не найден →
`spec file not found: <root>/<slug>.md`. Именно этот отказ человек получил из `/spec-approve spec-governance-per-spec.md`
(лог, стр. 9045).
**Правка:** порядок резолва: (1) путь как есть; (2) `cwd/.slim/spec/<arg>`; (3) `cwd/.slim/spec/<arg>.md`;
(4) поиск вверх до корня. При провале — сообщение со списком доступных slug.
**DoD:** `cd <project> && spec-approve <slug>` и `spec-approve <slug>.md` находят спеку.

### P0-3. Одобряет не-контракты (index / undeclared / archive / вне `.slim/spec`)
Единственная защита — наличие строки `Статус спецификации` (`STATUS_ANY_RE`). Следствия:
`ROADMAP.md` (token `roadmap` → GOV-7 **index**) одобряется; файл в `archive/` (GOV-6 **inactive**) одобряется;
любой путь вне `.slim/spec/` одобряется (`spec` в записи указывает куда угодно, гейт всё равно смотрит только
`<root>/.slim/spec/*.md` → запись инертна). Итог — **запись, которая «есть», но не даёт ничего**: тихий обман.
**Правка:** классифицировать (`spec_scope.classify`) и проверять активность (`spec_scope.is_active_spec`); разрешать
только `class == "spec"` **и** active. index/undeclared/archive/вне-каталога — refuse с объяснением (GOV-6/GOV-7).
**DoD:** `spec-approve .slim/spec/ROADMAP.md` → exit 2, «index, not a contract», записи нет;
`spec-approve .slim/spec/archive/x.md` → отказано.

### P0-4. Тихий провал флипа статуса
`STATUS_DRAFT_RE` требует ровно `` `draft` `` в бэктиках. Если токен без бэктиков или иной — флип не происходит,
но строка `Утверждено` вставляется и запись пишется ⇒ **одобрена спека, всё ещё помеченная `draft`**. Тот же класс
путаницы, что `ROADMAP.md:38` (называет approved-спеки `draft`).
**Правка:** после `updated = mark_approved(...)` — assert: хеш изменился **и** в `updated` есть `approved`; иначе
die «status flip did not apply; check the exact `Статус спецификации` line format» (файл на диске не трогать).
**DoD:** спека со статусом без бэктиков → exit 2, файл не изменён, записи нет.

- **P2-12. Неатомарная запись:** `write_text` без temp + `os.replace`; при Ctrl-C/ENOSPC — усечённый JSON, который
  `_load_records` **молча пропустит** (approval «исчезает» без диагностики). Правка: temp-файл в том же каталоге + `os.replace`.
- **P2-13. Нет readback:** хешируется in-memory `payload`, а не то, что легло на диск. Правка: после записи
  `assert sha256(spec.read_bytes()) == digest`, иначе die — это и есть честная проверка «unverifiable approval».
- **P2-14. Нет `--dry-run`:** показать, что изменится (статус, stamp, путь записи, предупреждения), не записывая.
- **P2-15. Документация:** USAGE, `command/spec-approve.md` (передаёт `$ARGUMENTS` как есть; нет списка; нет slug/`--all`),
  строка про `spec-approve` в `AGENTS.md`.

## 4. Sibling-дефект `spec-revoke` (обязателен тем же заходом)

`spec-revoke <one-spec.md>` удаляет **ВСЕ** `*.json` в `<APPROVALS_DIR>/<root_hash>/` (glob по каталогу), но в
`draft` возвращает только указанный файл. Остальные спеки остаются с `approved` в тексте, но **без записей** →
гейт и `spec-status` видят `no-approval` для всех → вся работа по проекту блокируется. Кроме того, при
аргументе-каталоге ревертятся все спеки.

**Правка:** удалять только запись(и), чей `spec` совпадает с указанным файлом (матчинг по содержимому, как
`find_valid_approval`); для каталога — явный `--all` (удалить все записи корня И вернуть все спеки в `draft`).
Печатать, что именно удалено.
**DoD:** `spec-revoke a.md` в каталоге из 2 одобренных спек → удалена 1 запись, `b.md` остаётся approved, allow сохраняется.

## 5. Целевой CLI-контракт

```
spec-approve [<slug>|<path/to/spec.md>|<dir>] [--all] [--changed] [--list]
             [--restamp] [--strict] [--dry-run] [--json] [--help]
```

- без аргументов = `--list`;
- остаётся **человеко-инициируемым**; агент его не вызывает;
- exit-коды: `0` ok (в т.ч. `--list`), `1` ошибка ввода/резолва, `2` отказ класса/пути
  (index/archive/undeclared/outside), `3` частичный отказ в `--all`;
- вывод по умолчанию — строка на файл + сводка; `--json` — массив (для агента/скриптов);
- **инвариант:** единственное допустимое изменение файла — «draft→approved + `Утверждено`»;
  при `--dry-run` — файл не пишется вообще;
- **инвариант:** печатается подтверждение `gate: allow|no-mandate|no-approval`, вычисленное независимым чтением
  `spec_scope`.

## 7. Контракт и радиация (что нельзя менять в одиночку)

- Формат записи читают: `spec_scope.find_valid_approval` / `approved_scopes` → `spec-status`, `docs-lint`, `dod-run`,
  `plugins/spec-gate.ts`; и `spec-revoke`.
- Матчинг — по `spec` (путь) + `spec_sha256`, **имя файла не значимо** ⇒ P1-10 (hash-имя) безопасен.
- Обязательные поля записи: `spec` (str), `spec_sha256` (str). Остальные — метаданные. **Добавлять** можно,
  **переименовывать/удалять** — ломает читателей (`spec-status` читает `data.get("spec_sha256")`;
  гейт — `record.spec` / `record.spec_sha256`).
- Инвариант «flip-before-hash» сохранить: хеш считается ПОСЛЕ флипа.
- P0-1 меняет наблюдаемое поведение, но не формат: запись остаётся валидной, sha256 спеки не меняется — совместимо.
- Любое изменение `spec-approve` требует синхронного обновления `command/spec-approve.md` и строки в `AGENTS.md`.
