# ADR 0002. Записи одобрения вне проекта; одобрение только человеком

- **Статус:** accepted
- **Дата:** 2026-09-27
- **Задача:** — (инфраструктурное решение лаборатории)
- **Автор:** orchestrator

> Формат: один файл — одно решение; нумерация непрерывная.

## Контекст

Первый дизайн предполагал, что маркером одобрения служит строка
`**Статус:** approved` внутри спецификации. Проблема очевидна: строка лежит в
файле, который агент имеет право писать (каталог `.slim/spec/**` — единственная
разрешённая область до одобрения). Значит, агент мог **сам себе выписать
одобрение**, просто отредактировав текст. Это подрывало весь Zero-Code Gate.

Дополнительно был зафиксирован дефект класса «два источника истины» (P0-1):
запись одобрения существовала, а спецификация по-прежнему сообщала `draft` —
потому что CLI одобрения не трогал текст спецификации. Любой агент, читавший
документ, видел `draft` и обоснованно отказывался работать, хотя гейт (по хешу)
пропускал запись.

## Решение

1. **Запись одобрения живёт вне проекта:**
   `~/.local/share/opencode/approvals/<sha256(root)[:16]>/<slug>.json`
   со схемой `{root, spec, spec_sha256, task, approved_by:"human", approved_at}`.
   Она не подконтрольна рабочему дереву и не пишется агентом в ходе обычной
   работы.
2. **Одобрение действительно, только пока хеш совпадает:**
   $\text{valid} \iff \operatorname{sha256}(\text{spec\_bytes}) = \text{record.spec\_sha256}$.
   Правка спецификации после одобрения **инвалидирует** одобрение — намеренно.
3. **`spec-approve` флипает статус ДО хеширования.** Порядок критичен: сначала в
   файле меняется `` `draft` `` → `` `approved` `` и ставится строка
   `- **Утверждено:** <ISO8601> (human)`, затем хешируется уже записанный
   payload, и только потом пишется запись. Хеширование до флипа навсегда
   инвалидировало бы одобрение. Это устраняет дефект P0-1 по построению.
4. **CLI одобрения — только для человека.** `bin/spec-approve`,
   `bin/spec-revoke`, `bin/gate-off`, `bin/gate-on` не лежат на `$PATH` и
   **сознательно не добавлены** в bash-allowlist: иначе агент мог бы одобрить
   себя через оболочку. Человек вызывает их абсолютным путём либо через
   TUI-команду `/spec-approve` (shell-блок команды исполняется клиентом, не
   агентом).
5. **Маркер отказа от гейта (`<root>/.slim/GATE-OFF`) лежит вне `.slim/spec/**`.**
   Поэтому попытка агента создать его инструментом `write` блокируется самим
   гейтом; симметрия с «одобрение только человеком» сохраняется.
6. **Отзыв.** `bin/spec-revoke` удаляет запись, возвращает строку статуса в
   `draft` и убирает строку «Утверждено»; операция идемпотентна.

## Последствия

### Позитивные

- Самовыдача одобрения агентом через правку текста спецификации больше не
  разблокирует запись.
- Одобрение автоматически протухает при любом изменении спецификации — не нужно
  помнить о ручном отзыве.
- Разделение «документ» и «разрешение» проверяемо: запись — машинный факт,
  строка статуса — человекочитаемое эхо, согласованное по построению с записью.

### Негативные (принятые компромиссы)

- Записи одобрения локальны для машины: они не коммитятся и не переносятся в
  репозиторий, поэтому на другой машине одобрение нужно выдать заново.
- Агент по-прежнему может *подделать* запись через `bash` (класс II) — это
  закрывается только жёстким барьером (см. ADR 0001).
- Существует аварийный выключатель `OPENCODE_SPEC_GATE=off`; он нужен для
  отладки и означает, что «одобрение» не является криптографической гарантией.

## Отвергнутые альтернативы

| Альтернатива | Причина отказа |
|---|---|
| Одобрение = строка `status: approved` в спецификации | Агент пишет `.slim/spec/**` легально → мог самовыдать одобрение. |
| Одобрение без хеша (только факт наличия файла) | Правка спецификации после одобрения не инвалидирует разрешение; расхождение документа и разрешения (дефект P0-1). |
| Хеш до флипа статуса | Навсегда инвалидирует собственную запись — прямое воспроизведение P0-1. |
| Запись одобрения внутри проекта (`.slim/approval.json`) | Пишется агентом через разрешённые инструменты или bash; переносится в git и «залипает» на чужих ветках. |
| Одобрение моделью/агентом по запросу | Противоречит требованию человеческого шлюза. |
