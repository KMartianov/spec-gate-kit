# ADR 0003. Состояние жизненного цикла выводится на чтение; отдельного хранилища нет

- **Статус:** accepted
- **Дата:** 2026-09-27
- **Задача:** — (инфраструктурное решение лаборатории)
- **Автор:** orchestrator

> Формат: один файл — одно решение; нумерация непрерывная.

## Контекст

Спецификация системы (§3) описывает автомат из семи состояний:
`INTAKE → DISCOVERY → SPEC_DESIGN → APPROVED → AUTONOMOUS_EXEC → VERIFY → DONE`
и правило R6 (остановка автономности после трёх подряд неудач на одной проверке).

Первая реализация вводила для этого отдельное хранилище `.slim/state.json`
(`state`, `updated_at`, `history[]`, `r6`) и CLI `bin/spec-status` с
подкомандами `set` / `history` / `r6 fail|pass`. Независимый архитектурный аудит
(`@oracle`) показал, что это решение переизобретает ровно тот класс дефекта,
который уже был исправлен в P0-1 (расхождение текста статуса и записи
одобрения), и вдобавок неработоспособно:

- **Второй источник истины.** `state` — кэш последнего элемента `history`, а
  `updated_at` дублирует `history[-1].at`. Читатели читают `state` (так проще),
  писатели дописывают `history` — они расходятся. Прозу «`state` — кэш `history`»
  можно считать документированным намерением разойтись.
- **Три пути расхождения.** (а) правка спецификации после одобрения
  инвалидирует хеш, но `state.json` остаётся `APPROVED`; (б) `spec-revoke`
  удаляет запись и возвращает текст, но `state.json` пишет только `spec-status`;
  (в) `spec-approve` пишет запись и текст, но не трогает `state.json` — гейт
  считает проект одобренным, а состояние говорит `SPEC_DESIGN`.
- **Вероятный дедлок.** `.slim/state.json` не лежит под `.slim/spec/**` и не
  входит в разрешённые цели гейта. Значит, переход `INTAKE → SPEC_DESIGN`
  (который происходит **до** одобрения) либо блокируется гейтом, либо требует
  carve-out для `.slim/*.json`, расширяющего гейт без выигрыша в принуждении.
- **Проверено экспериментально.** Гейт перехватывает только вызовы
  инструментов; `bash` не несёт аргументов-путей, поэтому
  `spec-status set DISCOVERY` проходит без блокировки и **без записи в
  аудит-журнал**. Счётчик R6 в файле, который агент может переписать через bash,
  не может ничего остановить (`exit 2` никто не читает), а смена `check-id`
  сбрасывает серию — то есть счётчик геймится.
- **Три имени одной сущности.** Поле `task`, имя файла спецификации и slug в
  записи одобрения — три названия одного и того же.

## Решение

**Отдельного хранилища состояния нет.** Состояние выводится на чтение из
проверяемых фактов:

$$\text{APPROVED} \iff \text{существует валидная запись одобрения},
\qquad \text{VERIFY/DONE} \iff \text{существуют артефакты доказательств DoD}$$

где $\text{valid} \iff \operatorname{sha256}(\text{spec\_bytes}) = \text{record.spec\_sha256}$.

Ключевой инвариант, делающий APPROVED непротиворечивым **бесплатно** (следствие
ADR 0002): поскольку `spec-approve` флипает строку статуса и только потом
хеширует записанные байты,

$$\text{record.spec\_sha256} = \operatorname{sha256}\big(\text{flip}(\text{spec})\big)
\;\Longrightarrow\;
\text{valid} \Longrightarrow \text{в текущих байтах стоит } \texttt{approved}$$

Обратное направление: возврат строки в `draft` меняет байты → хеш не совпадает →
гейт блокирует. Оба направления согласованы по построению, поэтому отдельная
переменная APPROVED не может добавить ничего, кроме возможности разойтись.

Практически:

- `.slim/state.json` **удаляется**; `bin/spec-new` его больше не создаёт.
- `bin/spec-status` становится **read-only отчётом** (`show [--json]`), который
  печатает выведенное состояние, путь и хеш спеки, путь записи одобрения и
  таблицу доказательств по проверкам. Подкоманды `set` / `history` / `r6`
  удаляются.
- Выведенные машинные состояния: `INTAKE` (спеки нет), `SPEC_DESIGN` (спека есть,
  валидного одобрения нет), `APPROVED` (одобрение есть, доказательств нет),
  `VERIFY` (одобрение есть, часть доказательств есть), `DONE` (одобрение есть,
  все проверки пройдены).
- Состояния `DISCOVERY` и `AUTONOMOUS_EXEC` **не выводятся** из артефактов и
  остаются словарём-прозой в спецификации; они ничего не принуждают и потому не
  заслуживают ни таблицы переходов, ни CLI.
- **R6 понижается до политики**: одна строка в промпте оркестратора («после трёх
  подряд неудач на одной проверке остановись и спроси человека»). Счётчик в
  файле запрещён. Исполняемым R6 станет только вместе с жёстким барьером
  (ADR 0001, уровень 2): только тогда процесс можно остановить.

## Последствия

### Позитивные

- Расхождение класса I становится **невозможным по построению** — состояние и
  разрешение суть одни и те же байты.
- Ноль новых писателей и ноль новых сущностей: удаляем файл, CLI и таблицу
  переходов вместо того, чтобы их добавлять.
- Спецификация уже версионируется git; её строка статуса читается человеком и
  машиной из одного места.
- Один ментальный шаг при отладке: «хеш совпал — одобрено».

### Негативные (принятые компромиссы)

- Тонкая история переходов (`who moved WHAT when`) не сохраняется. История
  уровня коммитов остаётся доступной через git (трейлеры `DDD-State:` — не
  запрещены, но и не обязательны).
- `DISCOVERY` и `AUTONOMOUS_EXEC` больше не машинные состояния — их нельзя
  проверить автоматически, и это честно отражено в отчёте.
- R6 остаётся политикой, пока не реализован жёсткий барьер; это осознанный отказ
  от ложной уверенности в пользу честности.

## Отвергнутые альтернативы

| Альтернатива | Причина отказа |
|---|---|
| `.slim/state.json` + `spec-status set/history` | Второй источник истины; три пути расхождения; дедлок с целями гейта; счётчик R6 геймится и никого не останавливает. |
| `state.json` как append-only лог (без `state`/`updated_at`) | Уже лучше, но всё ещё второй источник; выгода не покрывает цены, пока git даёт историю бесплатно. |
| Git-трейлеры `DDD-State:` как обязательный журнал | Хороший вариант (бесплатная история, tamper-evidence), но требует git в каждом проекте и гранулярности коммитов; оставлен как опция, не как обязательство. |
| Append-only хеш-цепочка `.slim/state.log` + верификатор | Обнаруживает правку, но не предотвращает её (класс II); третий механизм рядом с git ради меньшей пользы. |
| Персистентный счётчик R6 в файле | Геймится сменой `check-id`, пишется через bash, `exit 2` никем не читается. |
| Проверка «при установке APPROVED есть ли запись» | Закрывает вход, но оставляет все выходы открытыми (см. три пути расхождения); избыточна по отношению к выводу на чтение. |
