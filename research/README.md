# research/ — R&D: организация автономной работы OpenCode

> Рабочие исследовательские отчёты. Это **не** `docs/**` (там — нормативный эталон,
> принадлежащий человеку); `research/` — площадка R&D, без гейта.

## Вопрос исследования

Как лучше всего организовать работу вокруг OpenCode, чтобы агент **автономно**
создавал качественные и надёжные проекты: очереди, распределение задач, роли,
инструменты/утилиты, разделение ответственности, цикл разработки.

## Позиция

Текущая механика `spec-gate` (Zero-Code Gate, мандат `scope`, DoD-доказательства,
выводимое состояние) — **один из кандидатов, а не данность**. Серия ищет лучший
способ организации, в т.ч. отличный от него.

## Ограничения

- Работаем только внутри `spec-gate-kit`; реальный `~/.config/opencode` не меняем.
- Compute fence: ноутбук (6 ядер) — только чтение/рассуждение, без тяжёлых прогонов.
- Отчёты — вход в спеку на реализацию (Фаза 3).

## Метод

1. Опираться на артефакты кита (README, гайд, аудит, notes, ADR, `config/`) — не перевыводить сделанное.
2. Внешний ресёрч с цитатами; утверждения о ките — с `файл:строка`.
3. Синтез и риск — `@oracle`; консенсус по спорному — `@council`.
4. Отчёт каждого воркстрима — плотный, ≤ ~220 строк.

## Фаза 3: моделирование и эмпирика (M1–M4)

Цель — не «придумать», а **эмпирически выбрать** организацию работы: дискретно-событийная
имитация + Монте-Карло конвейера (контракты → лейны → approval → DoD → доказательства),
откалиброванная на измеренных числах (S2/S6, аудит), плюс анализ **реальных данных**
`opencode-lab` (`verify/*.json`, `spec-gate.jsonl`). Новое допущение: **любой нужный киту
функционал будет реализован в oclab** (kernel-изоляция, монтирование work по абсолютному пути,
проброс плагина/CLI, approvals RO-in / audit merge-out) — после утверждения уходит в запрос фич.
Значит Ф3 моделирует организацию работы ПРИ наличии HARD-субстрата, а не патчи soft-гарантий.

## Риски

- Спролл ресёрча → лимит объёма и фокус на решение.
- Дубль существующего аудита → переиспользовать.
- Overengineering «фабрики» → YAGNI; не проектировать «безусловное» как соглашение.
