> Воркстрим M2 Ф3 (`research/README.md:52-58`), исполнитель: `@python-expert`.
> Код и данные: `research/sim/` (`sim.py`, `params.json`, `test_sim.py`, `results/*.csv`).
> Вход модели: `research/M1-model-design.md` (§1 события, §2 параметры, §3 политики, §6 инварианты).
> Объём прогонов: **$12 \times 3 \times 10^4 = 3{,}6\cdot10^5$** репликаций + 7 свипов чувствительности (4 000 репликаций) + свип по `p_defect`.

## 1. Постановка

Дискретно-событийная имитация конвейера
`запрос` $\to$ $N$ контрактов (DAG) $\to$ лейны $\to$ approval $\to$
implementation $\to$ DoD-волна $\to$ evidence v2 $\to$ DONE, с ресурсами, ретраями, rework и R6.
Ресурсы: $L=2$ лёгких слота (draft/impl/rework), $H$ тяжёлых слотов (DoD-прогоны),
человек — последовательный сервер approval/консультаций. Модель времени волны — как в
S2/M1:

$$T_{\text{wave}} \approx \frac{1}{H}\sum_{c\in\text{heavy}}T_c + \max_{l\in\text{light}}T_l .$$

Единицы свидетельств двухъярусные (M1 §1.6):

$$\text{stale}_{cert}(i)=(\hat{G}_i\neq G(t))\lor d(t),\qquad
\text{stale}_{scope}(i)=(\text{scope.allow}(i)\cap\Delta F\neq\emptyset),$$

а терпимость определяется политикой: `global` перезапускает всех, `scope` — только
затронутые (политика C; при этом модель честно начисляет риск «скрытой» вне-scope связи
`shallow.*`, см. §4.3). `DONE` требует зелёной и свежей эвиденции по выбранному правилу:

$$\text{DONE}_i \iff a_i=1 \;\land\; \forall j:\ \big(e_{ij}=0 \land \hat h_{ij}=h_i
\land \text{fresh}_{ij}\big).$$

Заложены: flake-перезапуски с backoff, дефекты с вероятностью обнаружения
$p_{det}=1-(1-d_{suite})(1-d_{local})^{n}$, verification theater, rework-раунды (дефект
чинится с $p_{fix}$), правки спеки (инвалидация approval + эвиденции), R6 stop-and-ask
($\le 3$ подряд, затем пауза и человеческая консультация), коллизии writer-map при
отключённом single-writer, контеншн при $H>1$ (замедление $\times 1{,}3$, flake $\times 2$).
Вне модели: kernel-изоляция oclab, байтовые хеши, multi-root, MCP/сессионные эффекты —
это проверки M4 (§6), здесь же только организация работы.

## 2. Пространство политик

Политика — точка в 6-осном пространстве (`params.json`, ключ `policies`), а не код-ветка:

| ось | значения | смысл |
|---|---|---|
| `dedup` | $0/1$ | общий suite один раз на волну (stateless `wave-run`) |
| `staleness` | `global` / `scope` | правило сертификации: любой commit / только $\text{scope.allow}\cap\Delta F$ |
| `approval` | `per_contract` / `batch` | человек: по одному файлу / `--all/--changed` одним сидением |
| `heavy` | $1,2$ | число тяжёлых слотов $H$ (ноутбук / параллельные env) |
| `single_writer` | $0/1$ | сериализация контрактов с пересечением файлов (writer-map) |
| `sampling` | $0/1$ | risk-weighted сэмплирование DoD (дешевле, но слепее) |

Пресеты: **A** (status quo), **A_batch** (только батч-approve), **B_perc** (только дедуп),
**B** (дедуп+wave-run+батч), **C** (scope-shallow+`--changed`), **D** ($H{=}2$+single-writer),
**E** (сэмплирование), **A+D** (гонка без writer-map), **B+D**, **B+C**, **B+C+D**,
**B+C+D+E**. Добавление политики — строка в `params.json`, кода не требует.

### 4.4 Ранжирование

Практический Парето-фронт n16 по (wall, $\$$, $P(\text{false DONE})$, human):
**B+C** (самая быстрая), **B** (быстрая при минимальном риске), **B+C+D+E** (самая дешёвая,
но 5 % лж-DONE). Формальный фронт шире (9 из 12: `A_batch`, `B_perc`, `B`, `D`, `E`,
`B+D`, `B+C`, `B+C+D`, `B+C+D+E`) — при $10^4$ репликациях различия $\pm0{,}1$ п.п. по
$P(\text{false DONE})$ и $\pm\$0{,}02$ статистически на грани ($\pm\text{SE}\approx0{,}1$ п.п.),
и точки держатся на фронте шумом, а не эффектом. Отчётливо доминируются: **A**
(доминируется `B_perc`/`B`), **C** (`B+C`), **A+D** (`B+D`); **E** практически
доминируется `B+C+D+E` (та же скорость при 5,1 % против 10,4 % риска).

## 5. Вывод: какая организация лучшая и при каких условиях

1. **Базовый выбор — B+C** (дедуп DoD + stateless `wave-run` + scope-shallow `--changed`
   + батч-approve): $-47$ мин ($-19\,\%$) к wall, $-21\,\%$ к p95, ${-}\$0{,}35$, human $19 \to 6$ на 16
   контрактах. Цена — измеримый риск: $P(\text{false DONE})$ 2,2 % против 1,1 % у B и
   1,0 % у A, из которых 0,4 п.п. — «скрытая» вне-scope связь.
2. **Если важнее надёжность, чем последние 3 минуты — B** (тот же дедуп без shallow):
   самый быстрый среди политик с риском $\le$ status quo.
3. **$H>1$ не окупается при $N\le16$ и этой доле тяжёлых чеков**: B+D медленнее B,
   D/A+D $\approx$ A по wall при $\times 2$ flake. Параллелить имеет смысл только после дедупа и только
   если тяжёлая верификация — узкое место (в модели она 8–28 % wall; при росте доли
   e2e/asan-чеков — см. M3 R10 — вывод может измениться, это чувствительность к профилю).
4. **Батч-approve — не про wall, а про человека**; он становится критичным, как только
   человек медленный: при 30 мин/позицию A деградирует до 622 мин против 233 у B.
5. **Сэмплирование (E) — только с явным бюджетом риска**: $P(\text{false DONE})$ 10,4 %
   при $10^4$ репликаций; экономия heavy-времени 45 % не компенсирует потерю доверия.
   Комбинация B+C+D+E даёт самую низкую стоимость ($5,25) при 5,1 % риска.
6. **Порог применимости**: при $N\le4$ экономия wall $\approx$ 4 мин (7 %) — дедуп там
   нужен скорее ради human-нагрузки; с $N\ge8$ выигрыш монотонно растёт.

## 6. Проверки на артефакт (вшиты в `test_sim.py`, 13 тестов, 4,5 с)

Детерминизм (тот же seed $\to$ те же метрики); сохранение работы (все контракты доходят до
DONE, $\text{censored}=0$); `DONE` $\Rightarrow$ green+fresh+approved (ассерт в конце каждой
репликации); монотонность двух ярусов ($\text{stale}_{cert}=1 \land \text{stale}_{scope}=0$
при commit без пересечения scope — тест на внутренних структурах); дедуп (suites B
$\le 0{,}25\,$A, heavy $\le0{,}6\,$A); «A не быстрее B» (парные seed-ы, $\Delta$wall
$>5$ мин); батч режет interactions; E дешевле и рискованнее; C режет checks и начисляет
`hidden_misses`; $H$ и writer-map не нарушаются; R6 $\le$ лимита; границы $N=1$ и цепочка
$p_{dep}=1$; нулевой flake/theater $\to$ ноль лж-DONE.

## 7. Ограничения

- **Приоры, не замеры.** Длительности, approval-latency, flake-rate и $p_{defect}$ —
  допущения M1/M3; ранжирование проверено свипами (approval, flake, hidden, $p_{defect}$),
  но абсолютные минуты — не прогноз, а сравнение режимов. M3 R3 (вся сохранённая
  эвиденция зелёная) не даёт измерить истинный first-pass rate; prior выбран
  консервативным ($\approx 20\,\%$ сбоев), ранжирование к нему устойчиво (§4.3).
- **C реализована в оптимистичной семантике** README §5-P0.4 (DONE по scope-правилу);
  консервативное прочтение (SYNTHESIS §3b: `stale_cert` всё ещё гейтит DONE) свело бы C
  к оптимизации промежуточных волн. Вопрос H₂ — за M4; риск оцифрован (§4.3).
- **Агрегация чеков.** Battery одного контракта — один verify-job; распределение
  длительностей двухклассовое, хвост M3 R1 (p99 53 с, max 465 с) не воспроизводится.
- **Человек** — один последовательный сервер; нет параллельных апруверов, нет coarsening
  гранулярности контрактов; батч-триггер — упрощённая эвристика (порог/collect).
- **Не моделируются**: oclab-изоляция, диск/память env, сеть, MCP, дрейф канона команд,
  стоимость чтения экспортов, multi-root.
