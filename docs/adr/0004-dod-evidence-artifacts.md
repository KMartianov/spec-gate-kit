# ADR 0004. DoD-доказательства как артефакты `verify/<id>.json`

- **Статус:** accepted
- **Дата:** 2026-09-27
- **Задача:** — (инфраструктурное решение лаборатории)
- **Автор:** orchestrator

> Формат: один файл — одно решение; нумерация непрерывная.

## Контекст

Спецификация (§1.4) требует доказательного Definition of Done: задача завершена не
по заверению модели, а по автоматическому выполнению проверок (`ctest`, `pytest`,
ASan/UBSan, `nbval`, `sympy-verify`). Однако ничто не связывало слово «готово» с
фактом. Пункт §5 (чек-лист DoD) был человекочитаемым текстом; агент мог заявить
о выполнении, не выполнив ничего.

Отдельный вопрос — как хранить **результат** проверки. Он обязан быть (а)
машиночитаемым, (б) проверяемым, (в) диффабельным при ревью и (г) привязанным к
той версии спецификации, которая эти проверки предписывала.

## Решение

1. **Машиночитаемый блок DoD в спецификации.** В §5 спецификации размещается
   fenced-блок с info-строкой ровно `dod`, тело которого — **JSON**:

   ```dod
   {
     "checks": [
       {"id": "build", "cmd": "cmake --build build --config Release"},
       {"id": "test",  "cmd": "ctest --test-dir build --output-on-failure"}
     ]
   }
   ```

   JSON, а не YAML: в python3-stdlib нет YAML-парсера, а вводить зависимость
   ради одной секции несоразмерно.

2. **`bin/dod-run` — единственный писатель доказательств.** Он резолвит корень и
   спецификацию, разбирает блок `dod`, выполняет каждую команду и пишет
   `<root>/verify/<id>.json` со схемой:

   $$\texttt{\{check, cmd, exit\_code, started\_at, finished\_at, duration\_s, spec, spec\_sha256, tail\}}$$

   где `spec_sha256` — хеш байтов спецификации **на момент прогона**, а `tail` —
   последние ~2000 символов объединённого вывода. Код возврата `dod-run`: 0, если
   все проверки прошли, иначе 1.

3. **Доказательство привязано к версии спецификации.** `bin/spec-status` считает
   доказательство релевантным, только если
   $\operatorname{sha256}(\text{spec\_bytes}) = \text{artifact.spec\_sha256}$.
   Это то же правило инвалидации, что и для одобрения: правка спецификации
   протухает и одобрение, и доказательства — одна ментальная модель вместо двух.

4. **`DONE` зарабатывается, а не заявляется.**

   $$\text{DONE} \iff \text{валидное одобрение} \;\wedge\; \forall\, c \in \text{DoD}:\
   \text{verify}/c\text{.json}\ \text{существует} \wedge \text{exit}=0 \wedge
   \text{spec\_sha256 совпадает}$$

5. **Защита от разрушительных команд.** Перед запуском `dod-run` отказывается
   выполнять команды из denylist (`sudo`, `mkfs`, `dd if=`, `rm -rf /`,
   `rm -rf ~`, `shutdown`, `reboot`, `chmod -R 777`, …) и не пишет артефакт.

## Последствия

### Позитивные

- «Готово» становится проверяемым фактом: ярлык нельзя поставить, его надо
  заработать прогоном. Это прямо усиливает критерий §9.2 (автономность до DoD).
- Артефакты диффабельны и ревьюируемы: видно команду, код возврата, время и
  хвост вывода — то есть доказательство, а не утверждение.
- Инвалидация доказательств переиспользует уже существующий механизм хеша
  спецификации — ноль новой концепции.

### Негативные (принятые компромиссы)

- Артефакты можно подделать через `bash` (класс II) — как и всё остальное;
  подделка, однако, видна в diff. Закрывается только жёстким барьером.
- JSON-блок менее читаем для человека, чем YAML; компенсируется комментарием и
  тем, что команды всё равно правит человек.
- Хвост вывода ограничен 2000 символами — полный лог длинной сборки в артефакт не
  попадает (по замыслу; полный вывод остаётся в обычных логах сборки).
- Артефакты — новый каталог `verify/`, который следует коммитить (это
  доказательство, а не мусор).

## Отвергнутые альтернативы

| Альтернатива | Причина отказа |
|---|---|
| Доверять человекочитаемому чек-листу DoD | Непроверяемо; «готово» остаётся заявлением агента. |
| YAML-блок в спецификации | В python3-stdlib нет YAML-парсера; тащить зависимость ради одной секции несоразмерно. |
| Хранить результаты проверок в базе данных | Непрозрачно и не диффабильно при ревью; противоречит цели «доказательство как артефакт». |
| Артефакты без привязки к хешу спецификации | Доказательство пережило бы изменение ТЗ; возвращает класс I. |
| Выполнять проверки внутри самого `spec-status` | Смешивает read-only отчёт с побочными эффектами (запуск сборки/тестов); хуже разделение ролей. |
